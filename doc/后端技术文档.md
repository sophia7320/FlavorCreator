## 2. 认证体系

### 2.1 认证流程

```
客户端请求 /api/**
        │
        ▼
┌─────────────────────┐
│  AuthInterceptor     │  ← WebMvcConfig 注册，拦截所有 /api/**
│  preHandle()        │
├─────────────────────┤
│  1. UserContext.clear()
│  2. 判断 handler 是否标注 @Public
│     ├─ @Public → 有Token则解析userId，无则放行
│     └─ 无@Public → 无Token→401，有→解析后放行
│  3. UserContext.setUserId(userId)
└─────────────────────┘
        │
        ▼
   Controller / Service
        │  (通过 UserContext.getUserId() 获取用户)
        ▼
┌─────────────────────┐
│  afterCompletion()  │  → UserContext.clear()
└─────────────────────┘
```

### 2.2 Token 机制

| 类型 | 生成方式 | 有效期 | 存储 | 用途 |
|------|---------|--------|------|------|
| Access Token | JWT (HMAC256), claims: userId(L), openid(S) | 2小时 | 无状态 | API认证 |
| Refresh Token | UUID随机串 → 存Redis `rt:{uuid}` | 30天 | Redis | 刷新AT |

**JWT 声明**：`jti`(UUID)、`userId`(Long)、`openid`(String)

**Refresh Token Key**: `rt:{uuid}`, Value: `{"userId": 123, "openid": "oxxx"}` JSON, TTL: 30天

### 2.3 公开接口（ @Public 标注）

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/auth/login-wx` | POST | 微信登录 |
| `/api/auth/refresh` | POST | 刷新Token |
| `/api/community/recipe/{id}/comment` | GET | 评论列表 |
| `/api/ingredient/common` | GET | 常用食材 |
| `/api/recipe/list` | GET | 菜谱列表 |
| `/api/recipe/{id}` | GET | 菜谱详情 |

> 以上 6 个接口游客可访问。若请求中携带有效 Token，`UserContext.getUserId()` 可获取用户ID（用于判断点赞/收藏状态），不携带则为 null。

### 2.4 UserContext

```java
public class UserContext {
    private static final ThreadLocal<Long> USER_ID = new ThreadLocal<>();
    public static void setUserId(Long userId) { USER_ID.set(userId); }
    public static Long getUserId() { return USER_ID.get(); }
    public static void clear() { USER_ID.remove(); }
}
```

**生命周期**：preHandle() set → 业务处理 → afterCompletion() clear  
**设计意图**：Service 层不通过方法参数传递 userId，所有业务方法通过 `UserContext.getUserId()` 获取当前用户。

```

### 3.2 登录流程详解

```
POST /api/auth/login-wx  (@Public)
──────────────────────────────────────────────────────────
参数: { "code": "wx.login()返回的code", "userInfo": { "nickName": "...", "avatarUrl": "...", "gender": "1" } }

处理流程:

1. wxMaService.getUserService().getSessionInfo(code)
   │  调用微信 GET https://api.weixin.qq.com/sns/jscode2session
   │  返回: openid, session_key, unionid (可选)
   │  失败 → BusinessException(1001, "微信登录失败")
   │
2. 查询用户 → LambdaQueryWrapper.eq(User::getOpenid, openid)
   │
   ├─ 已存在 ─→ 返回 UserWithStatus(user, isNewUser=false)
   │
   └─ 新用户 ─→ 创建 User 实体:
                 · 设置 openid, unionid
                 · 优先使用前端传来的 userInfo (nickName, avatarUrl, gender)
                 · 兜底: nickname="创味机用户", gender=0
                 · createdAt/updatedAt = LocalDateTime.now()
                 · userMapper.insert(user)
                 · 返回 UserWithStatus(user, isNewUser=true)
   │
3. 生成令牌
   ├─ accessToken = jwtTokenUtil.generateToken(userId, openid)  (JWT, 2小时)
   └─ refreshToken = UUID.randomUUID().toString()               (30天Redis)
   │   refreshTokenService.store(userId, openid, refreshToken)
   │
4. 返回 LoginResponseDTO
   · token, refreshToken, expiresIn=300, isNewUser
   · user: { id, nickname, avatar, phone, gender }
──────────────────────────────────────────────────────────
返回: { code:200, message:"登录成功", data:{ token, refreshToken, ... } }
```

### 3.3 Token 刷新流程

```
POST /api/auth/refresh  (@Public)
──────────────────────────────────────────────────────────
参数: { "refreshToken": "UUID字符串" }

1. refreshTokenService.get(refreshToken)
   │  从 Redis 获取 rt:{uuid} → RefreshTokenData(userId, openid)
   │  不存在 → BusinessException(401, "刷新token无效或已过期")
   │
2. userMapper.selectById(userId)
   │  验证用户存在且 openid 匹配
   │  不匹配 → BusinessException(401, "用户不存在")
   │
3. 滚动刷新 (Refresh Token Rotation)
   ├─ refreshTokenService.delete(旧RT)      ← 旧RT立即失效
   ├─ newToken = jwtTokenUtil.generateToken(...)
   └─ newRefreshToken = UUID.randomUUID()
       refreshTokenService.store(userId, openid, newRT)
   │
4. 返回新的 token + refreshToken
──────────────────────────────────────────────────────────
```

### 3.4 登出流程

```
POST /api/auth/logout  (需认证)
──────────────────────────────────────────────────────────
参数: { "refreshToken": "..." }

1. refreshTokenService.get(refreshToken)
2. 验证 data.userId == UserContext.getUserId()  ← 防止登出他人
3. refreshTokenService.delete(refreshToken)      ← 删除Redis中的RT
```

### 3.5 依赖关系

```
UserController ────────────────────────────────────────────
  └─→ UserService (接口)
       └─→ UserServiceImpl (extends ServiceImpl<UserMapper, User>)
            ├─→ WxMaService (微信 API 调用)
            ├─→ JwtTokenUtil (JWT 签发/验证)
            └─→ RefreshTokenService (RT 存取删除)
```

### 5.4 发布菜谱 — 数据流

```
POST /api/recipe  (multipart/form-data)
  ┌─ @RequestPart("request") PublishRecipeRequestDTO (JSON)
  ├─ @RequestParam("cover") MultipartFile
  └─ @RequestParam("images") List<MultipartFile> (可选)
──────────────────────────────────────────────────────────
RecipeServiceImpl.publishRecipe()

1. userId = UserContext.getUserId()

2. 封面图片处理 (三步流程):
   a. validate(cover, "recipe-cover")   → 类型校验 + 大小校验(≤5MB)
   b. store(cover, "recipe-cover")      → 本地/COS 落盘
   c. moderate(coverUrl, "recipe-cover") → 内容审核(dev跳过)

3. 步骤图片处理 (可选, 遍历):
   同封面三步流程，scene="recipe-image"

4. 构建 Recipe 实体:
   ├─ name = request.getName()
   ├─ cover = coverUrl (空字符串如果无封面)
   ├─ images = objectMapper.writeValueAsString(imageUrls)  → JSON字符串
   ├─ ingredients/steps/tags 同样序列化为JSON
   ├─ authorId = userId
   ├─ source = 2 (用户)
   ├─ 所有count初始化为0
   └─ createdAt/updatedAt = now

5. recipeMapper.insert(recipe)

6. 返回 recipe.getId()
──────────────────────────────────────────────────────────
⚠️ 已知问题: 如果步骤5或6失败(JSON序列化失败等DB异常回滚),
   步骤2-3已上传到COS的文件会成为孤儿(文件无法回滚)。
```

### 5.5 菜谱列表 — 数据流

```
GET /api/recipe/list?category=home&difficulty=简单&keyword=鸡蛋&page=1&size=20
──────────────────────────────────────────────────────────
RecipeServiceImpl.getRecipeList()

1. 构建分页对象: Page<Recipe>(page, size)

2. 构建查询条件 LambdaQueryWrapper<Recipe>:
   ├─ category != null → eq(Recipe::getCategory, category)
   ├─ difficulty != null → eq(Recipe::getDifficulty, convertDifficulty(difficulty))
   │     "简单"→1, "中等"→2, "困难"→3
   └─ keyword != null → like(Recipe::getName, keyword)

3. 排序: orderByDesc(Recipe::getCreatedAt)

4. recipeMapper.selectPage(recipePage, wrapper)

5. 逐条转换 Recipe → RecipeListItemDTO:
   ├─ 查 User 作者信息
   ├─ JSON反序列化 tags
   └─ 格式化 createdAt (ISO_LOCAL_DATE_TIME)

6. 返回 Page<RecipeListItemDTO>
──────────────────────────────────────────────────────────
⚠️ 已知问题: RecipeListRequestDTO.taste 字段已定义但未在查询中使用
```

### 5.6 菜谱详情 — 数据流

```
GET /api/recipe/{id}
──────────────────────────────────────────────────────────
RecipeServiceImpl.getRecipeDetail(recipeId)

1. userId = UserContext.getUserId()  (可为null-游客)

2. recipe = recipeMapper.selectById(recipeId)
   不存在 → BusinessException(404, "菜谱不存在")

3. 原子递增浏览数:
   LambdaUpdateWrapper.setSql("view_count = view_count + 1")
   recipeMapper.update(null, wrapper)

4. 转换 Recipe → RecipeDetailDTO:
   ├─ 查 User 作者
   ├─ JSON反序列化: images → List<String>
   ├─ JSON反序列化: ingredients → List<IngredientItem>
   ├─ JSON反序列化: steps → List<StepItem>
   ├─ JSON反序列化: tags → String[]
   ├─ difficulty 整数→中文
   └─ JSON解析失败 → BusinessException(500, "JSON解析失败")

5. 判断用户互动状态 (仅 userId != null 时):
   ├─ isLiked = checkLiked(userId, recipeId, 1)    ← 查like表
   └─ isCollected = checkCollected(userId, recipeId) ← 查collection表

6. 返回 RecipeDetailDTO (含 stats, isLiked, isCollected)
──────────────────────────────────────────────────────────
```

### 6.3 点赞菜谱 — 并发安全设计

```
POST /api/community/recipe/{id}/like
──────────────────────────────────────────────────────────
CommunityServiceImpl.likeRecipe(recipeId)

1. userId = UserContext.getUserId()

2. 防重复检查:
   selectCount(like where user_id=userId AND target_id=recipeId AND target_type=1)
   > 0 → BusinessException(400, "已经点赞过")

3. 插入点赞记录 + 并发保护:
   try {
       Like like = new Like(userId, recipeId, targetType=1, now)
       likeMapper.insert(like)
   } catch (DuplicateKeyException e) {
       // 并发场景: 两个请求同时通过步骤2,一个插入成功一个失败
       throw new BusinessException(400, "已经点赞过")
   }

4. 原子更新菜谱点赞计数:
   UPDATE recipe SET like_count = like_count + 1 WHERE id = recipeId
   (使用 LambdaUpdateWrapper.setSql() 直接SQL,避免读-改-写竞态)

5. 返回 LikeCollectResponseDTO:
   ├─ isLiked = true
   ├─ likeCount = recipe.getLikeCount()  (此时已+1)
   ├─ isCollected = checkCollected(userId, recipeId)
   └─ collectionCount = recipe.getCollectionCount()
──────────────────────────────────────────────────────────
```

### 6.4 取消点赞 — 防负计数

```
DELETE /api/community/recipe/{id}/like
──────────────────────────────────────────────────────────
CommunityServiceImpl.unlikeRecipe(recipeId)

1. 直接删除点赞记录 (不存在也不报错):
   delete(like where user_id=userId AND target_id=recipeId AND target_type=1)

2. 防负计数更新:
   UPDATE recipe SET like_count =
     CASE WHEN like_count > 0 THEN like_count - 1 ELSE 0 END
   WHERE id = recipeId
   ↑ SQL CASE 表达式: 只有当前计数>0才-1, 防止并发或异常导致负数

3. 返回 LikeCollectResponseDTO
──────────────────────────────────────────────────────────
```

> 收藏 / 取消收藏逻辑完全同点赞，目标表为 `collection`，目标字段为 `collection_count`。

### 6.5 评论系统 — 父子结构

```
数据模型:
  Comment: id, userId, recipeId, parentId, content, likeCount

评论树构建流程 getComments(recipeId, page, size):
  1. 分页查询顶层的 WHERE parent_id IS NULL, ORDER BY created_at DESC
  2. 逐条转换 → CommentResponseDTO
     2.1 查 User 作者信息 (+ reply 作者)
     2.2 查子回复 WHERE parent_id = comment.id, ORDER BY created_at ASC
     2.3 查当前用户是否点赞该评论 (仅登录时)
     2.4 构建 CommentReplyDTO 列表

发表评论 addComment(recipeId, request):
  1. 创建 Comment (userId, recipeId, parentId, content, likeCount=0)
  2. 插入 comment
  3. 原子递增 recipe.comment_count

删除评论 deleteComment(commentId):
  1. 查评论 → 不存在→404, 非本人→403
  2. 删除评论
  3. 防负计数递减 recipe.comment_count

评论点赞 likeComment(commentId) / unlikeComment(commentId):
  同菜谱点赞/取消逻辑，targetType=2，更新 comment.like_count
──────────────────────────────────────────────────────────
```

### 7.3 状态计算 — 纯动态,不入库

```
computeStatus(expireDate):
  expireDate == null → "normal"
  daysLeft = ChronoUnit.DAYS.between(LocalDate.now(), expireDate)
  daysLeft < 0      → "expired"     (已过期)
  daysLeft <= 3      → "expiring"    (3天内临期)
  else               → "normal"

⚠️ 3天阈值是硬编码的,不可配置
```

### 7.4 食材列表 — 查询 + 内存筛选

```
GET /api/ingredient/list?sortBy=expireDate&sort=asc&category=蔬菜&status=expiring
──────────────────────────────────────────────────────────
IngredientServiceImpl.list()

1. 数据库条件:
   ├─ where user_id = userId
   ├─ where category = "蔬菜" (如果提供)
   └─ order by expireDate ASC (或 createdAt)

2. 查询全部匹配结果 → selectList(wrapper)

3. 内存过滤 (status):
   status != null && status != "all" →
      filter(ingredient -> computeStatus(expireDate) == status)

4. 每条 Ingredient → IngredientResponseDTO:
   └─ 计算 daysLeft 和 status (动态)

5. 统计汇总:
   ├─ totalCount = dtoList.size()
   ├─ expiringCount = 全量中status=="expiring"的数量
   └─ expiredCount = 全量中status=="expired"的数量
   ↑ 注意: expiringCount/expiredCount 从全量(未被status筛选的列表)计算,
      但totalCount是筛选后的大小,两者不一致。
```

### 8.1 Response<T> — 统一响应

public class Response<T> {

    private String message;
    private T data;

    public static <T> Response<T> success()                    // 200, null
    public static <T> Response<T> success(T data)              // 200, data
    public static <T> Response<T> success(String msg, T data)  // 200, msg, data
    public static <T> Response<T> error(Integer code, String msg)
    public static <T> Response<T> error(String msg)            // 500, msg
}
```

使用注解四合一: `@Data @Builder @NoArgsConstructor @AllArgsConstructor`

### 8.2 BusinessException — 唯一业务异常

```java
public class BusinessException extends RuntimeException {
    private final Integer code;  // 对应 ResultCode 常量

    public BusinessException(Integer code, String message) { ... }
    public BusinessException(String message) { this(500, message); }
}
```

**规则**: Service 层只能抛 `BusinessException`，禁止 `throw new RuntimeException()`

### 8.3 GlobalExceptionHandler — 全局异常处理

```
@RestControllerAdvice
GlobalExceptionHandler 处理6类异常:

┌─────────────────────────────┬──────────────────────────────┐
│ 异常类型                      │ 处理方式                      │
├─────────────────────────────┼──────────────────────────────┤

```

    │  失败 → BusinessException(2001, "图片格式不支持")

fileStorageService.store(file, dir)

### 10.2 LocalFileStorageServiceImpl 详解

```java
store(MultipartFile file, String dir):

1. 校验: file == null || empty → BusinessException(400, "上传文件为空")
2. 提取扩展名: UUID.ext
3. 日期目录: yyyyMM
4. 目标路径: {localPath}/{dir}/{yyyyMM}/{uuid.ext}
   (例: ./uploads/avatar/202605/a1b2c3d4.jpg)
5. Files.createDirectories(targetDir)  ← 自动创建目录
6. file.transferTo(targetFile)         ← 落盘
7. 返回URL: {urlPrefix}/{dir}/{yyyyMM}/{uuid.ext}
   (例: /uploads/avatar/202605/a1b2c3d4.jpg)
```

### 10.3 CosFileStorageServiceImpl 详解

```java
store(MultipartFile file, String dir):

1. 校验: file == null || empty → BusinessException(400)
2. 创建 COSClient (每次新建, 用完关闭)
   凭证: storageProperties.cos.secretId / secretKey
3. 提取扩展名 → UUID.ext
4. 构建 key: {dir}/{yyyyMM}/{uuid.ext}
5. 设置 ObjectMetadata (contentLength, contentType)
6. PutObjectRequest:
   - bucket: storageProperties.cos.bucket
   - key:    {dir}/{yyyyMM}/{uuid.ext}
   - ACL:    CannedAccessControlList.PublicRead
7. cosClient.putObject(putRequest)     ← 上传
8. 返回URL: https://{bucket}.cos.{region}.myqcloud.com/{key}
9. finally: cosClient.shutdown()       ← 释放连接
10. 异常: BusinessException(500, "文件上传失败")
```

### 13.2 JSON 字段管理

Entity 中的 JSON 字段全部使用 `String` 类型存储，通过 `ObjectMapper` 进行序列化/反序列化：

| Entity | JSON 字段 | 序列化方式 |
|--------|----------|-----------|
| User | preferences | writeValueAsString() | readValue() |
| Recipe | images | writeValueAsString() | readValue() |
| Recipe | ingredients | writeValueAsString() | readValue() |
| Recipe | steps | writeValueAsString() | readValue() |
| Recipe | tags | writeValueAsString() | readValue() |

### 13.3 计数冗余字段

三个实体维护了计数冗余，用于列表展示时避免 JOIN 操作：

| 实体 | 冗余字段 | 更新方式 |
|------|---------|---------|
| Recipe | like_count | UPDATE SET like_count = like_count ± 1 |
| Recipe | collection_count | UPDATE SET collection_count = collection_count ± 1 |
| Recipe | comment_count | UPDATE SET comment_count = comment_count ± 1 |
| Comment | like_count | UPDATE SET like_count = like_count ± 1 |

> 所有计数器更新使用 `LambdaUpdateWrapper.setSql("field = field + 1")` (直接 SQL 表达式)，避免"读-修改-写"竞态。减操作使用 `CASE WHEN field > 0 THEN field - 1 ELSE 0 END` 防负计数。

### 13.4 唯一约束 (并发防重)

| 表 | 唯一约束 | 作用 |
|----|---------|------|
| user | UNIQUE(openid) | 防止重复注册 |
| like | UNIQUE(user_id, target_type, target_id) | 防止重复点赞 |
| collection | UNIQUE(user_id, recipe_id) | 防止重复收藏 |

> 业务层先 `selectCount` 再 `insert`，外加 `catch DuplicateKeyException` 作为并发安全兜底。
