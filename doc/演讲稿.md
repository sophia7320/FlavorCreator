# 创味机后端架构设计 —— 技术演讲

*（投屏准备：IDE 打开项目，从 `BackendApplication.java` 开始）*

---

## 开场（30秒）

创味机是一个微信小程序，用户输入现有食材，系统智能推荐或 AI 生成菜谱。后端基于 Spring Boot + MyBatis-Plus，37 个 REST 接口，6 个业务模块。

我负责全部后端开发，下面聊聊架构设计和几个我觉得值得分享的设计决策。

---

## 一、模块化分层（1.5分钟）

*（投屏：BackendApplication.java）*

`BackendApplication` 用 `scanBasePackages` 显式声明了 6 个模块包：

```
auth      认证与用户实体
common    公共基础设施（拦截器、配置、工具类）
community 点赞/收藏/评论
ingredient 食材管理
recipe    菜谱 CRUD + AI 生成
user      用户信息/个人中心
```

每一层职责严格隔离：**Controller → Service（接口） → ServiceImpl → Mapper**，不能跨层调用。跨模块数据访问直接注入目标模块的 **Mapper**，不走 Service，避免循环依赖。

这是康威定律的体现——模块边界清晰，6 个人并行开发也不会冲突。

## 二、认证拦截器设计（2分钟）

*（投屏：AuthInterceptor.java）*

这是我觉得最值得讲的部分。整个认证模型的核心是两个概念：`@Public` 注解和 `UserContext`。

### `@Public` 注解

一个简单的方法级标记。标注了 `@Public` 的接口——比如获取菜谱列表、查看详情——游客也能访问。没标注的接口——发布菜谱、上传图片——必须登录。

### `AuthInterceptor.preHandle()` 执行逻辑

```java
// 第一步：解析 @Public 注解
boolean isPublic = hm.hasMethodAnnotation(Public.class);

if (isPublic) {
    // 有 Token 就解析出 userId 放到上下文，没有也放行
    if (token != null) {
        Long userId = jwtTokenUtil.getUserIdFromToken(token);
        if (userId != null) UserContext.setUserId(userId);
    }
    return true; // 游客和登录用户都放行
}

// 没 @Public → 无 Token 直接 401
if (token == null) throw new BusinessException(401, "未登录");

// Token 无效 → 401
Long userId = jwtTokenUtil.getUserIdFromToken(token);
if (userId == null) throw new BusinessException(401, "登录已过期");

UserContext.setUserId(userId);
return true;
```

### 为什么这个设计好

- **声明式注解**：不用写 if-else 判断，加了 `@Public` 就是公开，不加就需要认证，看一眼 Controller 就知道哪些接口对外暴露。
- **ThreadLocal 上下文**：`UserContext` 用 ThreadLocal 存储当前用户 ID。Service 层通过 `UserContext.getUserId()` 获取用户，方法签名里**从来不传 userId 参数**。拦截器保证每个请求的 ThreadLocal 生命周期—— `preHandle` 设置，`afterCompletion` 清空，绝对不会内存泄漏。

### JWT 部分

用 auth0 JWT 库，`userId` + `openid` 两个 claim，HMAC256 签名。密钥通过 `${jwt.secret}` 从配置文件读取，本地用默认值，生产环境由环境变量覆盖。开发者连密钥长什么样都不知道，安全问题从设计上杜绝。

## 三、AOP 日志 + 全局异常处理（1.5分钟）

*（投屏：LoggingAspect.java → GlobalExceptionHandler.java）*

### LoggingAspect

用 `@Aspect` + `@Pointcut` 切所有 Controller 和 Service 的 public 方法：

```java
@Pointcut("execution(public * flcr.backend..controller..*(..)) || 
           execution(public * flcr.backend..service..*(..))")
```

每次调用的入参、耗时、异常全部自动记录，不需要在每个方法里写 `log.info`。敏感参数——token、password、code——自动脱敏替换为 `***`。超过 200 字符的参数自动截断，防止日志膨胀。

### GlobalExceptionHandler

`@RestControllerAdvice` 统一拦截 6 种异常：

| 异常类型 | 返回 |
|---------|------|
| `BusinessException` | 业务错误，自定义 code |
| `MethodArgumentNotValidException` | `@Valid` 校验失败 → 400 |
| `ConstraintViolationException` | 方法级校验失败 → 400 |
| `HttpMessageNotReadableException` | JSON 格式错误 → 400 |
| `BindException` | 表单绑定失败 → 400 |
| `Exception` | 兜底 → 500 |

所有异常返回统一格式 `{code, message, data}`，Service 层只能抛 `BusinessException(code, message)`，不允许 `RuntimeException`——错误码用 `ResultCode` 常量，禁止硬编码数字。

### 组合效果

99% 的运行时异常都有明确的错误码响应给前端，排查问题时日志有完整的调用链和耗时，不需要加断点调试。

## 四、接口与实现分离 —— 策略模式（1.5分钟）

*（投屏：FileStorageService.java → Local/Cos/OSS）*

这是我最喜欢的设计模式应用。

### FileStorageService 接口

```java
public interface FileStorageService {
    String store(MultipartFile file, String dir);
    default void delete(String fileUrl) {}  // 默认空实现，不需要的不用管
}
```

### 三套实现，通过 `@ConditionalOnProperty` 切换

```java
// 本地文件（默认）
@ConditionalOnProperty(name = "flcr.storage.type", havingValue = "local", matchIfMissing = true)
public class LocalFileStorageServiceImpl implements FileStorageService

// 腾讯云 COS（云托管）
@ConditionalOnProperty(name = "flcr.storage.type", havingValue = "cos")
public class CosFileStorageServiceImpl implements FileStorageService

// 阿里云 OSS（占位）
@ConditionalOnProperty(name = "flcr.storage.type", havingValue = "oss")
public class OssFileStorageServiceImpl implements FileStorageService
```

### 同样的模式用在三个地方

| 接口 | 实现 | 切换条件 |
|------|------|---------|
| `FileStorageService` | Local → COS → OSS | `flcr.storage.type` |
| `ImageModerationService` | NoOp（跳过）→ COS CI（审核） | `flcr.moderation.enabled` |
| `RefreshTokenService` | InMemory（ConcurrentHashMap）→ Redis | `flcr.token.store` |

### 好处

本地开发时存储用本地磁盘、审核跳过、Token 存内存，一行配置写完。丢到云托管上改三个环境变量——存储用 COS、审核接腾讯云、Token 存 Redis——**代码一行不动**。

这叫**开闭原则**：对扩展开放，对修改关闭。

## 五、总结与答辩预判（1分钟）

这个项目用到的设计思路：

1. **分层架构** — Controller/Service/Mapper 不可跨越
2. **声明式认证** — `@Public` + `UserContext` ThreadLocal
3. **AOP 横切** — 日志、异常统一处理
4. **策略模式** — 接口抽象 + `@ConditionalOnProperty` 多实现切换
5. **TDD 驱动** — 每个功能先写测试再写实现

---

## 答辩预判

### Q：为什么不直接用 Spring Security？

小程序场景不需要表单登录、OAuth2 等复杂功能，自定义拦截器 71 行搞定，更轻量、可控。

### Q：ThreadLocal 不会内存泄漏吗？

`afterCompletion` 保证每次请求结束都 `clear()`。即使有异常没走到 `afterCompletion`，Spring 也保证了 `afterCompletion` 始终执行。

### Q：为什么跨模块用 Mapper 不用 Service？

避免循环依赖。比如 Recipe 模块需要查 User，注入 UserService 可能导致 `RecipeService → UserService → RecipeService` 循环。注入 Mapper 只是数据访问，没有依赖回环。

### Q：`@ConditionalOnProperty` 和 `@Profile` 有什么区别？

`@Profile` 选环境（dev/cloud/prod），`@ConditionalOnProperty` 选实现（local/cos/oss）。前者是部署维度的切换，后者是功能维度的切换。两者可以组合——cloud 环境 + cos 存储、cloud 环境 + 内存 Token。
